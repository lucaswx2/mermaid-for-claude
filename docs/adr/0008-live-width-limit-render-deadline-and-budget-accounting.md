# The width limit follows the live terminal width; a render deadline and full budget accounting

Wayfinder ticket #15 ran the size policy of ADR-0005 through the real `Stop` hook in the TUI (branch `prototype/size-policy`) and changed three things. First, the width limit is no longer a fixed 120 columns: it is the terminal width minus the four columns of the `Stop says:` indent (ADR-0001), read on every reply with a diagram; `MERMAID_FOR_CLAUDE_MAX_WIDTH` still overrides it, and 120 remains only as the fallback when nothing answers. ADR-0005 assumed a hook cannot see the terminal width; measured on Windows 11 with Windows Terminal, a hook process and all its children run on an invisible default console that always reports 120×30, but the console of the Claude Code process itself is the ConPTY one the terminal resizes, and `AttachConsole(pid)` plus `GetConsoleScreenBufferInfo` on a fresh `CONOUT$` handle returns its live width; a real console has a non-zero `GetConsoleWindow()`, a hidden one does not. Elsewhere the hook opens `/dev/tty` and reads its columns. Second, every diagram renders in a worker thread under a 3 s deadline, with the whole reply bounded at 7 s: the baseline renderer takes about 20 s on a flowchart chain 26 or more nodes deep and then throws (25 deep renders in 28 ms; direction and side branches change nothing), and Claude Code kills the hook at 10 s, which would have shown a hook error instead of a notice. Third, notices count against the 9,800-character output budget too; the prototype of #14 let them pile up past the 10,000-character cap. Rejected: keeping 120 fixed (the maintainer wants diagrams to fit the window of the moment); a background refresh of the width for the next reply (a process started by a hook dies with it, job object); PowerShell on every reply (about 1 s); a flowchart depth pre-check instead of a deadline (guards one known case, not the renderer).

## Consequences

- Windows needs one probe, not two helpers. Building #22 ran this design inside the real hook on Windows 11 and kept its core while dropping its PowerShell half. The core held exactly: every process in the hook's own chain reports `GetConsoleWindow() == 0` and 120x30, while `claude.exe` and the `powershell.exe` above it report a window and 188x49, so the window check is the discriminator and `AttachConsole` plus a fresh `CONOUT$` handle is the reading. PowerShell went because the probe can walk the ancestry itself with one Toolhelp32 snapshot, 15 ms for 260 processes against the 1.3 s a PowerShell start costs, and because `session-start.sh` can drive `csc.exe` directly in bash (with `-out:`, not `/out:`, which MSYS rewrites into a path). `hooks/console-width.cs` compiles to a 7 KB `console-width.exe` in 0.9 s cold and 0.2 s warm, once per machine, whenever the exe is missing or older than its source. The probe prints `<columns> <console pid> <its creation time>` and exits 0, or prints nothing and exits non-zero: a bash `$?` truncates to 8 bits, which would mangle a terminal wider than 255 columns, and the digits go to the standard output handle captured before `AttachConsole`, so they can never land in the reader's terminal whatever `AttachConsole` does to the standard handles. Measured inside the real hooks: `Keep each diagram under 184 columns` in the context line and `terminal=188/live`, `limit is 184` on every reply, on a 188-column Windows Terminal window.
- Nothing may wrap the probe, so it bounds itself. Because it finds the terminal by walking the processes above it, a bounding process joins that chain: an MSYS `timeout` forks twice, the walk stops at the dead link they leave, and the width comes back empty — measured, after `timeout 2` around it turned a working `184` context line back into `120`. The probe carries a 2 s deadline of its own instead, on a background thread that ends the process (measured: a build made to hang exits after 2111 ms), and the `Stop` hook's own bound is `spawnSync`, which kills the child without standing between it and its ancestors. What keeps a binary that cannot run from ever reaching the measuring run is `--self-test`, a mode that touches no console and can therefore be wrapped: `session-start.sh` runs it under `timeout 3` on whatever sits at the path, and deletes it when the answer is not `ok`. A binary wedged from its first instruction costs one session start 3.3 s, where it used to cost 30.5 s, and the next start compiles again.
- A compile is atomic or it did not happen. `csc.exe` writes to `console-width.exe.$$.tmp` and only a finished binary is moved into place, so a compile that is killed cannot leave a partial file whose fresh timestamp makes every later session trust it, and two sessions compiling at once cannot read a half-written one. With the self-test above it, a 7-byte stub planted with a timestamp in the future is deleted on the next session start and recompiled on the one after, and the live width comes back — the review's own repro, which before this had no way back.
- The cached pid carries the creation time of its process, and the walk is the fallback under it. `session-start.sh` caches the width, the pid of the console that answered and when that process started; the `Stop` hook hands the pair back, and the probe attaches only when `GetProcessTimes` agrees, because Windows hands a pid out again once its process is gone and a stranger's console would otherwise be reported as this terminal. Measured against the shell above `claude.exe`: the right pair attaches to it in 47 ms with no snapshot, while a wrong creation time, a zero and a dead pid each fall through to the walk. The walk is what needs every process in the chain alive, and a Windows shell chain was seen broken during #22, which is why the pair exists at all. The probe answers in 54-78 ms on an idle machine and about 160 ms under load, adding 60-150 ms to a reply with a diagram; `MERMAID_FOR_CLAUDE_MAX_WIDTH` short-circuits it, so a session that sets the override never spawns a probe or compiles anything. Only `session-start.sh` writes the cache: a reply that has to walk does not write the pair back, it just walks again until the next session start.
- The measurement comes out of the reply deadline, so it is capped at 400 ms. The 7 s deadline runs from bundle start (that is what keeps the hook inside Claude Code's 10 s), and the measurement happens before rendering, so a probe that answers slowly spends the reply's budget: at the 1 s first written it cost a trivial reply 1304 ms. 400 ms sits above the 265 ms the probe takes at the 90th percentile under load and is at most 6% of the budget, and a probe cut off at it costs nothing but a fall to the width cached at session start, which is the same number unless the window was just resized.
- Unix reads `/dev/tty` at zero cost: the bundle opens it and reads the window size of a `tty.WriteStream`, `session-start.sh` runs `stty size` on it. Still unverified on macOS and Linux as of the pull request for #22, which had only a Windows machine. It never throws, and it is bounded rather than trusted not to block: the bundle opens with `O_NONBLOCK`, so a terminal waiting on carrier cannot hold the reply, and the script runs the redirect inside `timeout 2` so the open is bounded too, not just `stty`. A failure falls to the cached width and then to 120, so an untested platform costs a wider default and nothing else. The spec carries the check.
- The ladder under the override is the live measurement (`live` on Windows, `tty` elsewhere), then the width `session-start.sh` cached for this session (`cache`), then 120 (`none`); the timing line names the rung it used. The cache lives outside the plugin root, under `$CLAUDE_CONFIG_DIR` or `.claude` in the home directory, as `mermaid-for-claude/console-width.exe` per machine and `mermaid-for-claude/terminal-<session id>` per session, swept after seven days along with any temporary a killed compile left. Never the OS temp directory, which is world-writable and no place to keep a binary the `Stop` hook executes. `session-start.sh` derives that path in bash and `src/terminal-width.ts` in TypeScript; a seam test runs both with `CLAUDE_CONFIG_DIR` unset so the two derivations have to meet on a real machine.
- The context line carries the width measured at session start; a resize is picked up by the next diagram reply, and by the next `/clear` or compaction for the context line.
- No automated test has a console, so `MERMAID_FOR_CLAUDE_FAKE_TERMINAL_WIDTH` stands in for the platform measurement in the seams and is `0` by default there, which keeps a developer running the tests inside a terminal seeing what CI sees. It answers as its own source, `fake`, so the timing line can never present it as a measurement, and it is read only beside `MERMAID_FOR_CLAUDE_TEST_SEAM`, which only the seam sets, so the variable left in a shell profile cannot change what a real session renders; a seam test pins that by comparing a run carrying it against a run without it. Everything below the measurement — the override, the cache file, the fallback, the notice text, the timing line — is asserted for real through the two hook scripts.
- Built-in renderers fit the live width (gantt compresses its axis to 76 columns on an 80-column window, kanban narrows); a baseline diagram wider than it becomes `could not render diagram i/N (type): 208 columns wide, limit is 184`, with the live number.
- The build ships two bundles, not one with a dynamic import (`build.mjs`): `dist/hook.mjs` (about 44 KB, the entry `hooks/stop.sh` runs) and `dist/render-worker.mjs` (about 1.5 MB, the only place the baseline renderer is evaluated). esbuild with `bundle: true` and a single `outfile` inlines `import()`, so one bundle would still hand the renderer to the main thread to parse; instead the worker is its own entry point and the hook names it by URL (`new URL('./render-worker.mjs', import.meta.url)`, which survives a plugin root with spaces or a drive letter). The hook bundle does carry the built-in renderers: the type table pulls them in, and the main thread needs it to name a block it never rendered.
- The worker costs about 250 ms per reply with a diagram: through `bash hooks/stop.sh` on Windows 11 / Node 24, `totalMs` runs 232 to 278 for a reply with one small diagram, of which about 8 ms is rendering and the rest is worker boot plus the worker's parse of the 1.5 MB bundle. A diagram over the deadline becomes `rendering took longer than 3 s`, the next one is tried in a fresh worker, and past 7 s the rest become `reply render deadline (7 s) exhausted`. Worst case measured: three 30-node chains plus a small diagram, 7.3 s, four notices.
- The budget keeps a 140-character reserve while blocks remain, so a closing `diagrams i/N to N/N skipped: output budget exhausted (9,800 chars per reply)` line always fits; 47 samples in one reply produce 9,699 characters.
- Kept as decided in ADR-0005 and confirmed in the TUI: 9,800 characters per reply (the spec's big block shows in full, no `<persisted-output>`; it measures 9,391 characters with beautiful-mermaid 1.1.3, against the 9,249 the prototype's own build of the renderer produced), compact padding for the six baseline types, "about 60 rows" in the context line.

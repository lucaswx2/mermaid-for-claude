# The width limit follows the live terminal width; a render deadline and full budget accounting

Wayfinder ticket #15 ran the size policy of ADR-0005 through the real `Stop` hook in the TUI (branch `prototype/size-policy`) and changed three things. First, the width limit is no longer a fixed 120 columns: it is the terminal width minus the four columns of the `Stop says:` indent (ADR-0001), read on every reply with a diagram; `MERMAID_FOR_CLAUDE_MAX_WIDTH` still overrides it, and 120 remains only as the fallback when nothing answers. ADR-0005 assumed a hook cannot see the terminal width; measured on Windows 11 with Windows Terminal, a hook process and all its children run on an invisible default console that always reports 120×30, but the console of the Claude Code process itself is the ConPTY one the terminal resizes, and `AttachConsole(pid)` plus `GetConsoleScreenBufferInfo` on a fresh `CONOUT$` handle returns its live width; a real console has a non-zero `GetConsoleWindow()`, a hidden one does not. Elsewhere the hook opens `/dev/tty` and reads its columns. Second, every diagram renders in a worker thread under a 3 s deadline, with the whole reply bounded at 7 s: the baseline renderer takes about 20 s on a flowchart chain 26 or more nodes deep and then throws (25 deep renders in 28 ms; direction and side branches change nothing), and Claude Code kills the hook at 10 s, which would have shown a hook error instead of a notice. Third, notices count against the 9,800-character output budget too; the prototype of #14 let them pile up past the 10,000-character cap. Rejected: keeping 120 fixed (the maintainer wants diagrams to fit the window of the moment); a background refresh of the width for the next reply (a process started by a hook dies with it, job object); PowerShell on every reply (about 1 s); a flowchart depth pre-check instead of a deadline (guards one known case, not the renderer).

## Consequences

- Windows needs one helper, not two. Building #22 ran this design inside the real hook on Windows 11 and kept its core while dropping its PowerShell half. The core held exactly: every process in the hook's own chain reports `GetConsoleWindow() == 0` and 120x30, while `claude.exe` and the `powershell.exe` above it report a window and 188x49, so the window check is the discriminator and `AttachConsole` plus a fresh `CONOUT$` handle is the reading. PowerShell went because the helper can walk the ancestry itself with one Toolhelp32 snapshot, 15 ms for 260 processes against the 1.3 s a PowerShell start costs, and because `session-start.sh` can drive `csc.exe` directly in bash (with `-out:`, not `/out:`, which MSYS rewrites into a path). `hooks/console-width.cs` compiles to a 6 KB `console-width.exe` in 0.9 s cold and 0.2 s warm, once per machine, whenever the exe is missing or older than its source. The helper prints `<columns> <console pid>` and exits 0, or prints nothing and exits 1: a bash `$?` truncates to 8 bits, which would mangle a terminal wider than 255 columns, and the digits go to the standard output handle captured before `AttachConsole`, so they can never land in the reader's terminal whatever `AttachConsole` does to the standard handles. Measured inside the real hooks: `Keep each diagram under 184 columns` in the context line and `terminal=188/live`, `limit is 184` on every reply, on a 188-column Windows Terminal window.
- The cached pid stays, and the walk is the fallback under it. `session-start.sh` caches the width and the pid of the console that answered; the `Stop` hook hands that pid back, and the helper walks only when there is no pid or that console is gone. The walk needs every process in the chain alive, and a Windows shell chain was seen broken during #22 (a parent had already exited), so the live width does not rest on it. The helper answers in 54-78 ms on an idle machine and about 160 ms under load, adding 60-150 ms to a reply with a diagram; `MERMAID_FOR_CLAUDE_MAX_WIDTH` short-circuits it, so a session that sets the override never spawns a helper or compiles anything.
- Unix reads `/dev/tty` at zero cost: the bundle opens it and reads the window size of a `tty.WriteStream`, `session-start.sh` runs `stty size` on it. Still unverified on macOS and Linux as of the pull request for #22, which had only a Windows machine; the code opens, reads and closes without ever throwing or blocking, and a failure falls to the cached width and then to 120, so an untested platform costs a wider default and nothing else. The spec carries the check.
- The ladder under the override is the live measurement (`live` on Windows, `tty` elsewhere), then the width `session-start.sh` cached for this session (`cache`), then 120 (`none`); the timing line names the rung it used. The cache lives outside the plugin root, under `$CLAUDE_CONFIG_DIR` or `~/.claude` when that directory exists and the OS temp directory when it does not, as `mermaid-for-claude/console-width.exe` per machine and `mermaid-for-claude/terminal-<session id>` per session, swept after seven days. `session-start.sh` derives that path in bash and `src/terminal-width.ts` in TypeScript, and a seam test keeps the two honest.
- The context line carries the width measured at session start; a resize is picked up by the next diagram reply, and by the next `/clear` or compaction for the context line.
- No automated test has a console, so `MERMAID_FOR_CLAUDE_FAKE_TERMINAL_WIDTH` stands in for the platform measurement in the seams and is `0` by default there, which keeps a developer running the tests inside a terminal seeing what CI sees. Everything below the measurement — the override, the cache file, the fallback, the notice text, the timing line — is asserted for real through the two hook scripts.
- Built-in renderers fit the live width (gantt compresses its axis to 76 columns on an 80-column window, kanban narrows); a baseline diagram wider than it becomes `could not render diagram i/N (type): 208 columns wide, limit is 184`, with the live number.
- The build ships two bundles, not one with a dynamic import (`build.mjs`): `dist/hook.mjs` (about 44 KB, the entry `hooks/stop.sh` runs) and `dist/render-worker.mjs` (about 1.5 MB, the only place the baseline renderer is evaluated). esbuild with `bundle: true` and a single `outfile` inlines `import()`, so one bundle would still hand the renderer to the main thread to parse; instead the worker is its own entry point and the hook names it by URL (`new URL('./render-worker.mjs', import.meta.url)`, which survives a plugin root with spaces or a drive letter). The hook bundle does carry the built-in renderers: the type table pulls them in, and the main thread needs it to name a block it never rendered.
- The worker costs about 250 ms per reply with a diagram: through `bash hooks/stop.sh` on Windows 11 / Node 24, `totalMs` runs 232 to 278 for a reply with one small diagram, of which about 8 ms is rendering and the rest is worker boot plus the worker's parse of the 1.5 MB bundle. A diagram over the deadline becomes `rendering took longer than 3 s`, the next one is tried in a fresh worker, and past 7 s the rest become `reply render deadline (7 s) exhausted`. Worst case measured: three 30-node chains plus a small diagram, 7.3 s, four notices.
- The budget keeps a 140-character reserve while blocks remain, so a closing `diagrams i/N to N/N skipped: output budget exhausted (9,800 chars per reply)` line always fits; 47 samples in one reply produce 9,699 characters.
- Kept as decided in ADR-0005 and confirmed in the TUI: 9,800 characters per reply (the spec's big block shows in full, no `<persisted-output>`; it measures 9,391 characters with beautiful-mermaid 1.1.3, against the 9,249 the prototype's own build of the renderer produced), compact padding for the six baseline types, "about 60 rows" in the context line.
